# WebSurf game 渲染帧 ↔ 权威帧 时序深度分析

> 2026-08-17 基于代码逐行核实（`game/src/**` + `src/ts-shared/**` + `src/phys/**`）。
> 本文是 `timing-game.md`（时序图速查）的深挖版：逐场景兜底同步时序 + 两个专题
> （垂直落体"锯齿 5.54"、"重力感觉偏重"）。以实际代码为准。

## 0. 架构定性

不是传统"服务端权威 + 客户端插值"模型，而是**双线平行模拟 + 反向校准**：

- **权威线**：Worker 内 64Hz 固定步长 PhysWorld（墙钟累积器驱动）；
- **渲染线**：主线程 rAF 变步长预测 PhysWorld（144Hz 级），**渲染的永远是预测线自身状态**，
  无快照插值、无快照缓冲；
- 两线喂**同一份输入**（双端同源），渲染线每帧被"权威速度外推"覆盖速度（位置不覆盖）；
- 大偏差时同步方向是**反的：以渲染线为准回写权威**（用户定调 2026-08-08，
  `src/ts-shared/phys/authority-calibrator.ts:8-14`）——因为渲染线精度（高帧率 + 零延迟）
  高于权威线（64Hz + 消息延迟）。

核心逻辑**不在 `game/src`**：权威循环 `src/ts-shared/auth/auth-loop.ts`、共享通道
`src/ts-shared/auth/shared-state.ts`、校准器 `src/ts-shared/phys/authority-calibrator.ts`；
权威物理 Rust 实现在 `src/phys/`（`game/crates/wasm/src/lib.rs:23` 只是 re-export）。

## 1. 两条线各自的时序

### 权威线（Worker，`auth-loop.ts`）

- 驱动：`setTimeout(loop, 4)` 自轮询 ≈ 250Hz（`auth-loop.ts:193-194`）；首次轮询只记墙钟
  基线不推进（`:197-199`），因此 wasm 就绪后约 4–8ms 才有第一个权威帧。
- 步进：`acc += 墙钟增量`，`while (acc >= fixedDt && guard < 64)`（`:201-209`）——
  累积器**不封顶**（低帧率不丢物理时间），单次轮询最多 64 步，欠步分摊到后续轮询。
- 每 tick（`stepPhysics`，`:114-190`）：`takeInput`（带 1200°/tick 饱和截断）→
  `phys.tick` 完整物理 → `writeAuthoritative` 写 SAB 双缓冲 + `timeMs = performance.now()`
  （**Worker 时钟**，tick 结束时刻，`:147-157`）→ 碰撞事件检测（land/blocked）。

### 渲染线（主线程，`game/src/renderer/renderer-main.ts:617-686`）

- rAF 驱动，帧内顺序固定（`:628-634`，整个时序设计的核心承重）：

  ```
  写输入 SAB → correctFromAuthority（读权威帧/兜底判定）→ calibrateVelocity（速度外推）
  → predPhys.tick(dt) → 相机 = 预测状态 → render
  ```

- 渲染 dt：`lastTickMs===0 ? 1/64 : min(真实dt, 0.1)`（`:625`）——首帧兜底 1/64s、
  帧间隔钳制 100ms。
- 渲染无条件执行（`:685`）；世界未就绪前渲染空场景，不黑屏不阻塞。

## 2. 逐帧耦合：速度外推校准

`calibrateVelocity`（`authority-calibrator.ts:247-262`）每渲染帧无条件执行：

```
dt = now渲染帧 − timeMs权威帧      // 跨线程时钟裸减，无偏移估计/平滑
v  = vel_A + accel_A × dt          // 仅当 0 < dt ≤ 0.1s
预测线.set_velocity(v)             // 只覆盖速度，不覆盖位置
```

- `accel_A` = 相邻两权威帧速度差/帧间隔（`:213-232`）；帧间隔 ∉ [0.001, 0.5]s → 置 0；
  各分量钳 ±20000（重力 800；碰撞瞬间速度跳变防外推爆炸）。
- 64Hz 权威 vs 144Hz 渲染：两权威帧之间约 2–3 个渲染帧共用同一份 `vel_A/accel_A`，
  外推逐帧拉大至约一个 tick（15.6ms），新权威帧到达即重置——锯齿式收敛，实测均值
  5.54 u/s/帧 ≈ 理论 800/144 = 5.556（详见专题 A）。
- **角度不参与校准**（`:243-245`）：视角由渲染线独占；权威仅碰撞事件可影响角度。

## 3. 兜底同步全景（逐场景）

### 3.1 启动期（无权威帧）

- SAB `V_A===0` → 读取返回 null（`shared-state.ts:259-260`）；校准器忽略 null
  （`authority-calibrator.ts:119`）。
- 渲染线此时已用同一份地图 JSON 自建预测物理（`buildPredictionWorld`，
  `renderer-main.ts:477-497`）从出生点独立模拟——**启动期渲染线无权威裸跑**。

### 3.2 首个权威帧 = 硬对齐

`predStarted===false` → 直接 `set_state` 权威全状态（`authority-calibrator.ts:132-139`）。
两线同出生点，通常无感知；若首帧到达前已有输入，预测线位移会被拉回权威起点
（一次可见的瞬间回拉）。

### 3.3 时间戳异常 / 权威停更

`dt≤0`（时钟异常）或 `dt>0.1s`（Worker GC/长任务/定时器节流/暂停恢复）→
**放弃外推，直接注入原始权威速度**（`:253-261`）。防陈旧加速度长时间外推爆炸；
代价是跳变瞬间速度不连续（轻微顿挫）。

### 3.4 碰撞事件微调（低频 postMessage 通道）

Worker 每 tick 检测（`auth-loop.ts:162-189`）：

- **land**：onGround 上升沿；
- **blocked**：速度>80 且前后速度差>250 且位移 < 预期×0.3（撞墙特征）。

主线程下一渲染帧应用（消息延迟约 1 个 rAF 周期），`applyCollisionCorrection`
（`authority-calibrator.ts:299-330`）：

- 距离门限 `dist < 60` 才处理，否则跳过（防视觉跳变，交给 3.5）；
- **land**：权威全状态覆盖（含权威碰撞速度 + onGround=true）；
- **blocked**：位置/角度取权威，**速度保留渲染侧**（避免权威速度注入抖动）。

这是权威侧**唯一**能影响渲染角度的通道。

### 3.5 大偏差反向同步（兜底体系核心）

触发判定（三条件 OR，`authority-calibrator.ts:194-197`，新权威帧到达时评估）：

| 条件 | 阈值 | 语义 |
|---|---|---|
| ① | dist > 500 | 绝对异常，强制同步，不看朝向 |
| ② | dist > 300 ∧ yawDiff ≤ 3° ∧ 同转向 | 位置大幅漂移但朝向一致 |
| ③ | dist ≤ 300 ∧ yawDiff > 45° | 位置接近但视角分叉（144Hz×3帧≈21ms 内甩视角不可能超 45°） |

触发后的完整时序链：

```
渲染帧 k：shouldSync 判定通过
  ├─ syncInFlight = true；lastSyncAt = now（250ms 冷却启动）
  ├─ onSyncRenderState(渲染线全状态) → 'sync-render-state' → Worker
  │    Worker：phys.set_state(渲染状态) + resetInput()（worker-dispatch.ts:156-180）
  └─ clearPendingInput()（清渲染侧 pendingDx/Dy/Keys）

在途期间（每个新权威帧）：
  ├─ 收敛：dist < 300 ∧ yaw ≤ 45° → syncInFlight = false
  ├─ 撤回监视：dist > 500 ∨ yaw > 45° → 方向反转！
  │    渲染线 set_state(权威全状态) + clearPendingInput + 退出在途 + 重置冷却
  └─ 其余 return（在途不重复触发）
```

关键点：

- **撤回**（`:168-181`）= "以渲染为准"后权威再次大幅分叉 → 判定上次方向选择错误，
  改回以权威为准回滚渲染。撤回分支在冷却检查（`:185`）**之前**——**不受 250ms 冷却限制**。
- 消息在途 1–16ms 内 Worker 仍用 SAB 旧输入跑 1–2 个 tick 后才被 `set_state` 覆盖，
  收敛判定因此晚 1–2 个权威帧达成（协议固有延迟，可接受）。
- 双侧清 pending 的原因：同步瞬间的旧增量注入新状态会二次分叉（`:53-54`）。

### 3.6 传送/重生显式重置

`resetTo`（`:268-275`）：`set_state` + 速度清零 + `clearPendingInput` + **`clear()` 全部
校准状态**（含 `curAuth=null, lastVa=-1, predStarted=false`）——旧权威帧无法把玩家拉回，
下一个新权威帧重新走 3.2 首帧硬对齐。传送必须**双线同发**（`app.ts:229-233`）：只发
渲染线的话权威留在原地，>500 兜底立刻反向同步——"传送被拉回"bug 的根因修复。

### 3.7 后台标签页（当前最大时序黑洞）

**全代码无 `visibilitychange` 处理**。只有 `window.blur`（`app.ts:195-200`）清键盘与
渲染侧 pending，但 `InputBridge.addInput` 是故意 no-op（`input-bridge.ts:24-26`，
输入统一由 `RendererMain.tick` 写 SAB）——而 rAF 后台停转，**SAB `I_KEYS` 冻结在最后
写入的键位**。后果链：

1. 后台 rAF 停 → 渲染线冻结、SAB 键位冻结；
2. Worker `setTimeout` 被节流（Chrome 后台 ≥1s/次，深度节流 1 次/分钟），但每次触发
   `guard<64` 单轮最多补 1s 物理时间——权威线**以冻结键位继续模拟**（按着 W 进后台
   就继续走）；
3. 回前台瞬间：渲染线 = 冻结点，权威线 = 冻结键位跑了 N 秒的位置 → `dist>500` 必然
   触发 3.5；若权威欠步巨大（深度节流累积几分钟 acc），`sync-render-state` 只 set_state
   **不清累积器**，权威继续狂奔补步 → 可能再次分叉 → 撤回回滚 → 来回拉扯/大跳变。

建议：`visibilitychange` 隐藏时写 keysMask=0（或 auth loop 暂停 + `reset()` 累积器）。

### 3.8 兼容模式（无 SAB，postMessage 回退）

`shared-state.ts` MsgState（`:150-228`）：输入每渲染帧 `input` 消息、权威帧每 tick
`phys-frame` 消息，但主线程**只缓存最新帧**（`:189-191`）。时序差异：事件循环 + 结构化
克隆延迟更高（平均多 1–2 帧），外推 dt 系统性偏大更易顶到 0.1s 窗口退化成原始速度注入；
丢帧使 `computeAuthAccel` 帧间隔 >0.5s → accel 置 0 → 外推停摆。功能可用、精度降级
（状态栏"兼容模式…性能降级"，`app.ts:74-76`）。

### 3.9 错误路径

Worker `onerror` / `error` 消息 / 双侧 wasm 加载失败 → 仅 `setError` 上屏（`app.ts:85,
89-90, 126-128`；`worker-dispatch.ts:94-99`）。**无 Worker 重启、无 panic hook、无通道
看门狗**——出错后循环带病继续或静默停摆；渲染线靠 3.3 停更兜底退化成裸跑预测。

## 4. 深层时序风险

1. **后台标签页漏洞**（3.7）——唯一必然触发的时序缺陷。
2. **反向同步 vs 权威追赶竞争**：`sync-render-state` 不重置累积器，权威欠步大时拉扯。
3. **死亡逻辑不对称被兜底掩盖**：`set-death-threshold` 有定义有处理器但 game 从未发送
   （`worker-types.ts:48-51` / `worker-dispatch.ts:206-214`）→ 权威 `death_y` 恒为
   -100000（`mod.rs:89`），渲染侧却设了 `set_death_y(bbox.min.y)`（`renderer-main.ts:273`）。
   渲染线坠亡重生后 `dist>500` 反向同步把权威拉回 spawn——**"看起来正常"实为兜底链
   掩盖协议缺失**，权威侧死亡/重生从未真正执行。
4. **跨线程时钟裸减**：Worker `performance.now()` 与主线程直接比较，无偏移估计。现代
   浏览器专用 worker 与所属文档共享 time origin（HR-Time 规范）此处成立；旧环境常数
   级偏移会被 0.1s 窗口掩盖成持续轻微超前/滞后。
5. **渲染 dt 钳 0.1s 无 CCD**：卡顿恢复首帧单步 100ms，surf 场景 1000+ u/s 单帧位移
   可超 100 units，存在穿碰撞几何风险；靠 >500 兜底纠回但中间一帧可能视觉穿墙。
6. 死配置：`teleportGateTicks` 默认 1 与注释"默认 3"不符（`config.ts:110` vs `:28-29`），
   且 Rust 侧忽略该参数（`mod.rs:216` 仅保留签名）。

## 专题 A：垂直落体"锯齿 5.54"是什么

### A.1 出处

`authority-calibrator.ts:241` 注释"垂直落体实测：锯齿 5.54≈理论 5.56，滞后偏差消除"
的实测来源是 **`game/scripts/phys-dual-pipe.mjs`（双管道垂直落体测试，node 直接跑
wasm）**，数字是 mode=e（v4.6 外推校准，即线上方案）的输出（`:184`）：

```
预测速度锯齿: 均值=5.54x/帧 最大=… (理论 ~5.556/帧)
```

**它不是重力值，也不是偏差值**——它是"自由落体时渲染线（预测）速度的**逐帧变化量**"：
测试把每帧 `|vy[i] − vy[i−1]|` 记入 `predVelJumps`（`:152-154`），取第 20 帧后均值。
参数：`TICK=1/64`（权威）、`PRED=1/144`（渲染帧）、`G=800`、从 y=500 落体 1.5s（`:42-46`）。

理论值推导：自由落体 vy = −G·t，两个渲染帧之间 Δvy = −G × (1/144) = **−5.556 u/s/帧**。
实测均值 5.54 ≈ 5.556（差 0.3%）——即渲染线速度以"每帧恰好一帧重力"的速率平滑下降。

### A.2 它验证的机制（为什么叫"锯齿"）

测试对比 5 种校准方案（`:5-14` 的 mode a–e 演化史）：

- **mode d（v4.5，旧方案）**：每渲染帧 `set_velocity(最近权威速度)`——直接注入**陈旧**的
  64Hz 权威速度。一个权威 tick（15.6ms）内约 2.25 个渲染帧共用同一 `vel_A`：
  每帧被重置回陈旧值，再被本帧重力拉低——渲染速度呈**阶梯/锯齿**状，且系统性**滞后**
  真实值最多一个权威 tick（12.5 u/s @64Hz）。这就是"锯齿"和"滞后偏差"的名字来源。
- **mode e（v4.6，线上方案 = `calibrateVelocity`）**：`vel_A + a×(t_now − t_A)` 外推。
  自由落体时权威加速度恰好 = −G（两权威帧速度差/tick），外推与真实落体完全重合 →
  权威帧到达时的重置不再产生跳变，渲染速度每帧平滑 −5.556。**"锯齿 5.54≈理论 5.56"
  就是"外推恰好消除了滞后"的量化证明**。

细节：测试的 `timeMs` 记 tick**结束**时刻（`:129-131` 注释）——记开始时刻会让外推多算
一个 TICK 的滞后；生产代码 `auth-loop.ts:154` 同样在 tick 后打戳。

### A.3 5.54 与 5.556 的微小差值来源

- 144/64 = 2.25 非整数：权威帧相对渲染帧的落点相位循环，重置瞬间的微残差取平均略低；
- 半重力前后各半（`player.rs:946-948`）的离散积分 vs 连续理论值。

均 <0.5%，属离散化噪声，非 bug。

### A.4 这个数字证明什么 / 不证明什么

- **证明**：渲染管线中重力**恰好施加一次、净加速度精确等于 800 u/s²**。若校准与
  预测 tick 双重施加重力，逐帧变化会是 ~11.1；若外推方向错，均值显著偏离且最大值
  跳变（mode d 特征）。
- **不证明**：任何关于"重力感受"的结论——它只覆盖纯垂直自由落体（无输入、无碰撞），
  不涉及跳跃、空中转向、surf 坡面等场景（见专题 B）。

## 专题 B："重力感觉偏重"分析

### B.1 数值层：全部是 CS 系标准值（"数值没问题"的感知是准确的）

| 参数 | 本作 | CS 系参考 | 位置 |
|---|---|---|---|
| gravity | 800 | sv_gravity 800（Source 默认） | `config.ts:98` / `player.rs:17` |
| jumpSpeed / jump_height | 302 / 57.0 | 跳跃冲量 ≈301.99（apex 57u，滞空 0.755s） | `config.ts:99` / `player.rs:38, 560-561` |
| maxSpeed / walk / crouch | 250 / 130 / 85 | 250 / 130 / 85 | `config.ts:100-107` |
| accelerate / stopSpeed | 10 / 100 | 10 / 100 | `config.ts:102, 104` |
| airAccel / 空速帽 | 150 / 30 | surf 服务器通行 100–1000 / 30 | `config.ts:103` / `player.rs:22-23` |
| hull | 32×32×72 / 蹲 54 | CS:S 玩家碰撞体 | `config.ts:118-122` / `player.rs:31-33` |
| 眼高 | 64.09 / 46.04 | Source view_ofs | `player.rs:34-35` |
| FOV | 73.6（垂直） | 16:9 下 ≈106° 水平 ≈ Source 90(4:3) 折算 | `config.ts:126` |

跳跃链路自洽：`jump_height = 302²/(2×800) = 57.005`（`params.ts:49`）→
`jump_velocity = √(2×800×57.005) = 301.99`（`player.rs:560`）——往返一致，无双重缩放。

**结论：重力数值没有问题，且专题 A 的 5.54 直接反证了"管线内重力被放大/双重施加"
不存在**（否则逐帧速降会是 11.1）。"感觉偏重"另有来源，按影响排序如下。

### B.2 真实候选来源

**① 反预速规则（影响最直接，纯规则差异）**
`noPrestrafe: true`（落地水平速度硬钳到 runSpeed 250）+ `bhopSpeedClamp: true`
（起跳时水平速度钳到 1.1×maxSpeed = 275，`player.rs:549-556, BHOP_MAX_SPEED_FACTOR=1.1`）。
多数 surf 服务器允许 250–280+ 的 prespeed 上板；本作每次落地都封 250——上板/上坡
"吃速度"，直接读作"沉/粘"。这与重力无关，但手感常被归因为"重力重"。

**② 权威 64Hz 主导速度增益（与专题 A 同源的架构性间接影响）**
`calibrateVelocity` **每渲染帧无条件**覆盖预测线速度（`authority-calibrator.ts:247-262`），
覆盖基准是权威帧外推值。因此预测线自己积累的空中加速（air-accelerate 在 wishdir 上
每帧加的横向速度）在下一次覆盖时被丢弃，只保留"当前这一帧"的增量——**渲染轨迹的
速度增益率实际由权威线 64Hz 积分决定**（等效 64-tick 服务器）。空中 strafe 增益随
积分步长细化而增（每步都会把 wishdir 分量补到 30 u/s 帽），参照系是 100-tick 服务器
或本地高帧率的玩家会感觉空中加速"发闷/吸住"。这是双管道设计的固有代价，专题 A 验证
的垂直落体恰好检测不到它（无横向输入）。

**③ 跳跃冲量无补偿通道（推导，未实测）**
land/blocked 有 phys-event 微调通道（3.4），**跳跃没有**：跳起的瞬间，渲染线 tick 内
vy=302，但随后 1–2 帧内权威帧尚未包含这次跳跃（最多 ~15.6ms + 通道延迟），
`calibrateVelocity` 会把 vy 拖回旧权威值，直到权威跳跃 tick 落地。表现为起跳头一两帧
偏"闷"（位置损失推导约 1–3u，MsgState 兼容模式下延迟翻倍更明显）。与 ② 同属
"离散速度突变无法外推预测"的机制盲区。

**④ 无终端速度钳制**
Source 有 `sv_maxvelocity 3500`；本作 Rust 侧无对应钳制（`player.rs` 无 maxvelocity，
air_move 注释"无空中速度上限"，`:953`）。长落差的冲坠会超过 CS 体验上限，越落越快，
长坡场景"更重"。

**⑤ 感知因素**
FOV/眼高/单位全标准，但浏览器窗口宽高比若偏离 16:9（垂直 FOV 固定 73.6），水平 FOV
随之收窄 → 速度感/坠落感变化；friction 4（`config.ts:101`）是 CS 1.6 值（CS:S 默认
4.8、CSGO 5.2），地面更滑而非更重，可排除。

### B.3 验证建议

- ②③ 可用 `phys-dual-pipe.mjs` 扩展实验直接量化：给预测线加横向输入对比双管道速度
  曲线；跳跃场景记录渲染线 vy 首 5 帧。
- ① 用面板/配置临时关 `noPrestrafe`、`bhopSpeedClamp` 对比手感。
- ④ 若要对齐 Source 体验，在 Rust 侧补 3500 u/s 全速度钳制。

## 专题 C：渲染线与权威线的垂直速度等价性（Q1）

**结论：成立。** 纯弹道（无碰撞、无输入）下，两线的垂直速度/位置对积分步长**严格分区不变**，
实测差为 f64 舍入级；"同一刻计算"时误差恒等于 0（同一段确定性代码、同一组 f64 运算）。

- 理论：`air_move` 为半重力中点法（`player.rs:946-948`）——速度 Σg·dt 与步长划分无关；
  位置用中点速度积分对线性变化的速度精确。
- 实测（`game/scripts/phys-rate-parity.mjs` 实验①）：自由落体 1s，64Hz vs 144Hz vs
  混合分区，Δy=1.99e-13、Δvy=4.21e-12；y=100.000、vy=−800.000 与理论逐位吻合。
  无 brush 纯落体 vy 每 tick 恰好 −12.5（=g·dt，`phys-diag-flat.mjs`）。

因此**手感偏重的来源不是积分误差**，而是碰撞交互中的速度损失，按量级排序：

1. **DIST_EPSILON=0.03125u + PUSH_OUT=0.1u 的每次命中嵌入**（`world.rs:114,155`、
   `player.rs:441-443`）：命中频率越高吃掉越多。surf 滑行实测（实验②）：3s 滑行后
   64Hz 与 144Hz 终态差 ~5u / ~5.2u/s（64Hz 侧碰撞更频繁、损失略大）。长滑累积可观。
2. **首触相位差**（实验②④）：两线首次触坡事件相差半权威 tick（t=0.813 vs 0.819s），
   之后轨迹永久错开数 unit——出坡高度因此天然带 ±数 unit 抖动。
3. **事件性归零分支**（见专题 E 嫌疑清单）——与步长无关，两线同构地暴露。

**关键修正**：由于 `calibrateVelocity` 每渲染帧用权威外推覆盖渲染线速度，玩家实际感受的
速度增益≈权威线（64Hz）的行为 + 2~3 帧相位。"渲染线精度高"只在位置/角度成立；速度以
权威为准 → 权威线在碰撞中多吃的损失会直接传导为手感。

## 专题 D：坡顶入坡"幻影碰撞"——brush 凸角无 bevel 平面（Q2 根因）

**结论：根因不是采样率，是碰撞几何缺陷。** brush 碰撞 = 凸半空间交集（`clip_planes`，
`world.rs:118-183`），**凸棱处不生成 bevel 平面**——Minkowski 扩张后的各半空间交集
在角点附近**过近似**实体，形成"幻影碰撞区"：

- 坡 brush 的起始竖直切面（如 z=0，法线 −z）扩张后等效一堵**幻影墙**，从玩家盒前沿
  z=−16 起、覆盖角点以下全部高度；
- 坡面平面本身在坡起点上方同样有**幻影楔形延伸**（扩张 ~16u = hull 半宽）。

实测（`phys-rate-parity-v2.mjs` 场景 B，平顶台+60°坡，同一起点仅步长不同）：

| 参数 | 64Hz（权威） | 144Hz（渲染） | 结果 |
|---|---|---|---|
| H=2.5u, vz=300 | 撞幻影墙全停（终速 6.3，悬停台缘） | 仅擦损 22u/s 顺利入坡下滑（2247） | **★Δvel=2242** |
| H=4.0u, vz=500 | 未触发，滑入坡（2424） | 撞幻影区全停（终速 2.8，悬停） | **★Δvel=2422** |

即用户描述的"渲染不会踩到的坡顶在 tick 计算中检测到碰撞"**双向都成立**——哪条线
倒霉取决于采样相位（64Hz 单步位移 4.7~12.5u，跨过整个楔形核心区；144Hz 单步 2.1~5.6u，
相位错开时可擦边而过）。慢速/贴缘通过时必然有一侧命中。

**连锁失败模式（双线软锁）**：渲染线若被幻影楔形"钉"在坡起点上方（悬停、速度≈0），
权威线正常滑走 → dist>500 → 反向同步（渲染为准！）把**权威拖回悬停态** → 两线一起
卡死在半空。实测复现（变体实验：渲染线沿坡面后移 25u 后 t=1.236 触发，权威 v=(−752,430)
被覆盖为渲染的 (−3,0)）。

**通用解法（按优先级）**：

1. **brush 构建期生成 bevel 平面**（标准 Quake/Source 解法，也是本仓 tri 碰撞已有的
   做法——`world.rs:240-256` 为三角形边补侧平面，brush 应同样处理）：对 brush 每条
   凸棱（相邻平面外法线叉积），插入一张经 brush 包围盒裁剪的 bevel 平面，消除角点
   过近似。**与步长无关，两线同治，是根治方案。**
2. 碰撞子步进（单步位移 > 阈值时拆步重放）只缓解穿隧、**不解决幻影墙**（几何仍在，
   仅缩小倒霉相位窗口），不作为本问题主修。
3. 临时缓解：地图侧避免让玩家贴缘低空切入坡起点（加导流几何）。

## 专题 E：坡底"还在坡上但速度规律归零"（Q3 根因）

**结论：与兜底频率无关；规律来自摩擦衰减被逐帧灌入。** 完整机制链（双管道复现，
`phys-rate-parity-v2.mjs` 实验⑥）：

1. 权威线先一步到达坡底平地（首触相位差 + 容差累积漂移，实验②实测 3s 漂 ~5u）；
2. 权威落地 → `walk_move` 摩擦（friction=4）线性衰减：每 tick 掉 `speed×4/64`
   （1271 u/s → 0 仅需 16 tick = 0.25s）；
3. `calibrateVelocity` **每渲染帧**把衰减中的权威速度灌给仍在坡上 surfing（无摩擦）的
   渲染线 → HUD 速度（采样自预测线，`app.ts:305-328`）呈**规律线性衰减到零**，
   而画面上人还在坡上；
4. 收尾二选一：权威 land 事件到达且 dist<60 → `set_state` 硬吸到落地点（画面瞬间
   贴底）；dist≥60 跳过 → 渲染线以灌入的衰减速度在坡上爬行，直到 dist>500 触发
   反向同步。

实测速度序列（实验⑥，两线同时落地的干净情形）：`1271 → 127 → 46 → 0`（0.4s 内，
正是摩擦线性衰减曲线被灌入的形态）。

**兜底频率澄清**：反向同步是**事件驱动**（新权威帧到达 ∧ dist>500 ∧ 冷却 250ms 已过），
不是周期性；land/blocked 微调也是事件驱动；唯一逐帧执行的是速度灌入（144Hz）。
所以"规律"不可能来自兜底节奏，只能来自被灌入信号自身的规律（摩擦衰减）。

若观察到"反复归零-恢复"循环，则是专题 D 的幻影钉住 + 反向同步拖回的组合（双线软锁
的振荡变体），同样以修 bevel 为根治。

**修复方向**：
- 主修：专题 D 的 bevel 平面（消钉住/拖回）；
- 辅修：land 事件微调门限 60u 对 surf 场景偏大（渲染线还在坡上 50u 时被硬吸），
  可考虑仅当渲染线自身也接近着地（vy<0 且 |vy| 小）时才应用 land snap；
- 摩擦灌入本身是"权威速度即真值"设计的必然，若要保留 surf 手感，可在权威帧
  `onGround=true` 而渲染线 `surfing=true` 时暂停速度灌入（分歧窗口 <1 tick，代价极小）。
