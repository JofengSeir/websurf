## 5. 三类不一致：识别方法与处理规则（取证只用代码）

### 5.1 A 类：代码与注释不符

| 识别方法（纯代码取证） | 处理 |
|---|---|
| **计数对撞**：注释中的数量词（"导出 N 个 API""M 个字段"）用 `grep 'pub fn'` / 字段计数实测 | 以实测改数量词；枚举改为"全列 + 行号" |
| **常量对撞**：注释里常量值与源码常量逐一比 | 以源码为准；注释改为指向常量表，避免二次抄写 |
| **签名对撞**：注释描述的参数/返回与当前签名比对 | 重写为当前签名语义；不改签名 |
| **标识符对撞**：注释提到的函数/模块/字段是否已不存在 | 删除或改指当前标识符 |
| **编译反证**：改注释后 `cargo check` / `npm run typecheck` 仍通过（若失败说明误改代码 → 回滚并上报） | 见 §10 |

**规则**：① 以代码为准；② 删除无法验证的历史叙述；③ 提交信息写明"对撞方式 + 实测值"；④ **不得把旧注释内容搬进新稿**。

### 5.2 B 类：代码与新稿文档不符

| 识别方法 | 处理 |
|---|---|
| `node src/scripts/check-doc-drift.mjs`（行数声明 / 锚点越界 / 路径失效 / 歧义） | 锚点越界必须 0；路径失效逐条处置 |
| **锚点抽样开箱**：随机抽 ≥5 个锚点，打开确认该行即所述内容（体检只查越界、不查错位） | 错位即改锚点，再抽 5 个 |
| **清单对撞**：文档中的接口/参数/文件清单与代码逐一比对 | 以代码重列；清单必须可由命令再生 |
| **可执行判据**：文档给的验证命令实际执行 | 命令失败 → 修命令或标注"当前失败（原因）"并上报 |

### 5.3 C 类：误引用（引用了旧注释、旧文档或已失效路径）

| 识别方法 | 处理 |
|---|---|
| **双跳核查**：文档锚点 → 打开该行 → 若该行是注释，先按 A 类核对该注释与代码是否一致 | 注释本身错的先修注释 |
| **孤儿引用**：引用了已删除的注释/章节/文件，或指向 `test/game-core/**`、已退役 harness 工程的路径 | 删除引用或改指当前代码事实 |
| **来源审查**：全稿 grep 禁用措辞（§6.3），命中即疑似 C 类 | 改写为"代码 X 行表明…" |
| **引文比对**：不得出现"注释说…""文档说…"式二次引用 | 一律删除并上报 |

**规则**：禁止二次引用；引用**代码事实**而非注释文字；无法确认出处者删除。

## 6. 书写规范

### 6.1 通用（沿用仓库约定）

- 行尾 **CRLF**；UTF-8 **无 BOM**；无行尾空白；无 `CR CR LF`
- 代码/路径/命令用 ASCII 直引号；正文中文
- 一级标题唯一；层级不跳级；同表列数一致；代码块围栏标语言
- 不新建 `xxx-v2.md`；就地更新并记录提交信息（CHANGELOG 已删除，由 WG10 从源码重建）
- 锚点写作 `` `文件:行号` ``（相对仓库根），必须可定位

### 6.2 内容规范

- 每条断言带源码锚点；数字带单位（HU、B、槽、Hz、ms）
- 关键函数必须写**不做什么**（反向说明）
- 注释写"为什么 / 坑 / 约束"，不写"这行做了什么"
- 文档每篇首行标注：事实基准日期 + 读码方式 + 上下游

### 6.3 来源审查：禁用措辞（S4 grep 必须 0 命中）

| 禁用 | 原因 |
|---|---|
| "据文档 / 据注释 / 原设计 / 历史上曾经 / 原来的实现" | 以旧稿为依据，违反 B1/B2 |
| "应该 / 可能 / 大概是 / 似乎 / 推测" | 无证据断言，违反 B3 |
| "详见旧版 / 见 archive / 见历史讨论" | 旧稿已删除，且不存在可回读的归档副本，此类指向必失效 |
| 任何 `test/game-core/**` 锚点，或已退役 harness 工程的锚点 | 两者均不在工作区，锚点不可定位 |

## 7. 统一术语表（强制）

### 7.1 运行时与协议

| 术语 | 含义 | 禁用说法 |
|---|---|---|
| 权威帧 | Worker 固定 64Hz 模拟输出的状态帧（pos/yaw/pitch/vel/eyeHeight/onGround/timeMs） | 服务器帧、主帧 |
| 预测线 | 主线程全速物理 + 渲染，读权威帧做**速度对齐**（位置不覆盖） | 自造词 |
| SAB | SharedArrayBuffer（game/debug 512B；原 harness 的 192B 布局随工程退役，不再作为口径） | 共享内存块（须写 SAB + 字节数） |
| 槽 / slot | SAB 或 `state_out` 内按索引定位的字段 | 位置、格子 |
| 双缓冲 | S_A[0]/S_A[1] 交替写，`V_A` release 递增，读者读 `(V_A-1)&1` | 乒乓缓冲 |
| seqlock | 发布序守卫（偶=稳定、奇=写入中） | 版本号 |
| tick / 渲染帧 | tick = 固定 64Hz 物理步；渲染帧 = rAF | 混用"帧" |
| 解耦线 / 耦合线 / tick 线 | **已退役口径**：原为 harness 三模式对照的术语，该消费方随退役工程删除；共享层 `src/ts-shared/decoupled/decoupled-loop.ts` 仍在（其语义需另行读码取证） | 模式一/二/三 |

| 术语 | 含义 |

## 10. 冲突处理与上报

### 10.1 文件级

| 场景 | 规则 |
|---|---|
| 同文件被两组同时改 | 按 §9.1 顺序串行；未排到不得提前动手 |
| 改注释时代码被改 | 以合并后代码重跑 S0/S1；冲突不自解则挂起上报 |
| 两篇文档对同一事实表述不同 | 各自回源码取事实；仍不同 → 上报（附双方锚点） |
| 需改文件名/移动文件 | **禁止**自行改名移动；上报（涉及 index/README/链接全量更新） |

### 10.2 必须停下上报（不得"先写着"）

1. 代码自相矛盾（两模块对同一不变量冲突）；
2. **疑似代码缺陷**（注释/文档与代码不符且看起来是代码错）——只记录不修；
3. 无法在代码中定位的断言；
4. 锚点越界且无法判断指向；
5. 需改代码/构建配置才能让文档成立；
6. 涉及 `test/game-core`、夹具、依赖锁、CI 配置的改动意图；
7. **读到注释与代码冲突时**：按代码写，不得把旧注释内容记入新稿（只记"已修 A 类 n 条"计数）。

### 10.3 上报格式

```markdown
## 上报：<文件>
- 类型：A / B / C / 疑似缺陷 / 冲突 / 越权意图
- 现象：<一句话>
- 证据：<代码 文件:行号>（不引用旧注释/旧文档原文）
- 已做的定位：<读码 / 命令 / 实测>
- 建议：<改写措辞 / 删除断言 / 需主控裁决>
- 当前处置：挂起（未提交）
```

**升级**：工作组 → 主控（本文件维护者）→ 仓库 owner。上报文件保持未提交，不得带 `[待确认]` 提交。
