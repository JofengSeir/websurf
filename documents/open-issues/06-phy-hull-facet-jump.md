# 06 · `.phy` 凸包表达不了曲面坡 ⇒ 玩家在 facet 交界处被一帧抬升十几 HU

**状态**：**已处置**（根因是 `step_move` 的抬升闸门判据，已修，见 §7）
**发现日期**：2026-10-05
**复现地图**：`test/maps/surf_666.bsp`
**涉及对象**：`models/props/666/s1_ramp1b.mdl`（.phy 凸包，走 `triJson` / `trace_box_tri_entries`）

**同一条坡上的后续问题**：[`07-is-position-free-vs-trace.md`](07-is-position-free-vs-trace.md) ——
本条（弹飞）修好后，玩家在同一位置改为**原地抖动卡死**（`check_stuck` 每 tick 被 `is_position_free`
判为不空并挤出玩家）。两条是同一处 `.phy` 凸包几何的两个侧面，**成因不同、修法不同，需一并评估**。

再落回原高度，接着 `on_ground` 翻转、`contact_ticks` 归零，触发传送检测被送回出生点。owner 的
原话是「被弹走」。

owner 提供的路径文件 `phys-path-20261005-103745.json`（`render` 采样，主线每 rAF 物理步一个节点）：

```
t=46286  (-13533.71, 14568.78, -9790.87)  vY=+524.6 HU/s   一帧 +9.70 HU
t=46302  (-13533.71, 14573.68, -9795.03)  vY=+293.7 HU/s   一帧 +6.42 HU
t=46719  (-13534.40, 14579.62, -9899.06)  vY=+728.5 HU/s   一帧 +12.80 HU

`PhysWorld::build_world` + `set_state` + 逐 tick `tick(1/64, 0x01, 0, 0)`（0x01 = forward）。

起点取 owner 路径的首个采样 `(-13534.50, 14560.03, -8895.50)`，yaw = 0（实测 yaw=0 是唯一让 z
减小且 x 不动的朝向）。

```

    0    -8895.5   14560.03   0.00   true
  220    -9742.2   14560.03   0.00   true
  230    -9785.2   14560.03   0.00   true
  231    -9789.1   14571.58  11.55   true    ← 弹飞
  232    -9793.0   14569.70  -1.88  false

  240    -9824.2   14560.03 -11.51   true    ← 落回

**与 owner 路径同一位置、同一量级**（z −9789.1 vs −9790.87；+11.55 HU vs +9.70 HU）。

> 教训：复现时 `triJson` 必须喂 `export_model_phy_colliders()`。喂 `'[]'` 会得到一个**看起来完全
> 合理但与owner 现象无关**的结果——玩家会稳稳走在一条世界 brush 的五棱柱顶上、y 恒定、走完整条
> 都掉不下去。本条缺陷整条位于模型三角网格路径，与世界 brush 平面路径无关。

## 3. 根因证据

### 3.1 头顶没有东西，不是"抬升撞到台阶"

在 `x = -13534.5, y = 14560.03` 处沿 +y 扫掠 18 HU（`step_move` 抬升用的正是这一条）：

```
z=-9785.2   up-sweep frac=1.00000   （什么都没碰到）
z=-9789.1   up-sweep frac=1.00000
z=-9793.0   up-sweep frac=1.00000
z=-9797.0   up-sweep frac=1.00000
```

所以 +11.55 **不是**被上方几何顶上去的。

### 3.2 真正的坡面比玩家脚下高 11.55 HU

同一点向下扫掠：

```
z=-9785.2   down-sweep frac=0.99993  命中 y=14560.03  n=(0,1,0)        n.y=1.0000
z=-9789.1   down-sweep frac=0.35793  命中 y=14571.59  n=(-0.614,0.786,0.069)  n.y=0.7864（38.2°）
z=-9793.0   down-sweep frac=0.46924  命中 y=14569.58  n=( 0.614,0.786,0.069)  n.y=0.7864
z=-9797.0   down-sweep frac=0.44986  命中 y=14569.93  n=( 0.614,0.786,0.069)  n.y=0.7864
```

**⇒ 玩家一直踩在 14560.03，而该处真实坡面在 14571.59，低了 11.55 HU。** 走到模型末端时，
地面追踪从一块 facet 换到相邻 facet，一次判定把玩家抬高 11.55 HU。

### 3.3 那个面上没有任何顶点 ⇒ 它是凸包的大三角形

- 该列的**世界 brush** 顶面只有：`14558.1（52.13° 的五棱柱顶）`、`15616.0（楼板）`、
  `13952.0`，**以及 y 为负的若干层**。**14571 附近没有任何 brush。**
- 120 HU 内的**模型 .phy 顶点**只有一条：`s1_ramp1b` 的 `(-13536.0, 14557.69, -9802.9)`——
  正好在玩家脚边高度，且 z 几乎等于 hull 的 z 下界。

**⇒ 命中面所属的三角形，其三个顶点都在 120 HU 之外。**

`s1_ramp1b` 实例的 AABB：`x -13984..-13088, y 13952..15148, z -11136..-9803`，108 个顶点。
`export_model_phy_colliders()` 只返回 `{name, surfaceprop, vertices}`，**三角形由 Rust 侧按凸包
生成**（`src/phys` 的 `TriMesh`）。一条凸包 facet 常常横跨上千 HU，**其平面延展远超顶点范围**，
所以"面上没有顶点"是正常的，不能据此排除。

**⇒ 根因：`s1_ramp1b` 的 `.phy` 凸包把一条曲面坡近似成少数几个大平面；相邻 facet 之间存在
十几 HU 的高度落差，而地面追踪只认"赢得 enter_frac 的那一张"，于是在 facet 交界处把玩家从一块
吸到相邻块。** 这不是物理算错——物理拿到什么就算什么——**错的是几何表达**：凸包表达不了曲面。

## 4. 已排除的解释

| 解释 | 排除依据 |
|---|---|
| 被上方台阶顶上去 | 向上扫掠在所有被测 z 都是 `frac = 1.00000`（§3.1） |
| `STEP_HEIGHT = 18` 允许跨台阶，所以是规则问题 | 抬升根本没撞到东西（§3.1）；且 `STEP_HEIGHT` 的语义是"跨台阶"，这里没有台阶 |
| 世界 brush 的问题 | 该列 14571 附近无任何 brush；玩家踩的 52.13° 五棱柱属于另一处几何（§3.3） |
| chamfer 平面的问题 | chamfer 只在世界 brush 路径（`clip_planes`）生成，模型三角网格路径不经过它 |

## 5. 走过的弯路（留档，避免重走）

1. **一直只测世界 brush 路径。** 误把 `x -13984..-13088 / y 13952..14560 / z -9856..-8576` 的
   五棱柱当成 owner 的坡，量出"脊线斜率 0.00°、走完整条都站得住"的结论。那是另一处几何。
   入口判据：`export_model_phy_colliders()` 里有 `models/props/666/s1_ramp1b.mdl`。
2. **`triJson` 喂了 `'[]'`。** 结果是玩家稳稳站在世界 brush 上，与owner 现象完全不符。
   只要 owner 的现象涉及模型，必须先确认 tri 路径已加载。
3. **在 `step_move` 里加"直接移动被不可站面挡住就不许抬升"的闸门——无效，已回滚。**
   弹飞那一刻水平移动**根本没被挡住**（水平扫掠 `frac = 1.00000`），障碍是在 `step_move` 内部
   "先移后抬"的第二步才遇到的，闸门放错了位置。
4. **误判 `s1_ramp1b` 不存在。** 它不在实体 lump 里（`parse_entities()` 全文只有 6 处 "ramp"，
   属 `s6ramp2` 与 `filter_ramps`）；它是**模型**，名字只出现在 `export_model_phy_colliders()`
   的 `name` 字段里。查实体名找不到就应转查模型名。
5. **`state_full_json` 的位置字段是 `origin`（数组），不是 `pos_x/pos_y/pos_z`。**
6. **`debug_trace` 返回值下标**：`[0]=fraction, [1..3]=normal, [4]=start_solid, [5]=all_solid`。

## 7. 处置结果（2026-10-05，已完成）

### 7.1 真正的根因（比 §3 更精确）

§3 定位到了「玩家被一帧抬 11.55 HU、真实坡面比脚下高 11.55 HU」这个事实，但当时把它归因到
「凸包 facet 落差」。**读`step_move` 的代码后找到了确切机制**，与 facet 表达精度无关：

```rust
let mut tr = world.trace(&p.origin, &[origin.x, origin.y + STEP_HEIGHT, origin.z], &mins, &maxs);
if !tr.start_solid && !tr.all_solid {
    p.origin = tr.end_pos;      // ← tr 无命中时 end_pos == 扫掠终点 == 头顶 +18 HU
}
```

**`trace` 在无命中时把 `end_pos` 设为扫掠终点。抬升扫掠在头顶空旷时必然无命中，于是这一行等价于
「每 tick 把玩家无条件抬 `STEP_HEIGHT`(18 HU)」。**

- **平地上完全不可见**：紧接着的落回扫掠会把玩家拉回原高度，最终 origin 看不出异常。
  （第一版回归测试就栽在这里——平地上断言「不得有抬升」，撤掉修复照样通过。）
- **只要「新位置的地面比原地高」，抬升就会胜出**：抬到 +18 → 前移 → 落回扫掠踩到那块更高的
  地面 → 被采纳。§3.2 里那块高 11.55 HU 的坡面正是这个角色。

所以这是**一处判据缺失**，不是几何表达问题：facet 落差只是让这个 bug 有了可见的后果。

### 7.2 改动

`src/phys/player.rs` 的 `step_move`，采纳抬升后位置的条件加一道 `fraction < 1.0`：

```rust
if tr.fraction < 1.0 && !tr.start_solid && !tr.all_solid {
    p.origin = tr.end_pos;
}
```

语义：**只有真的撞到上方东西才抬**。头顶空旷时不抬——本来也没有要跨的障碍。

### 7.3 验证

真实 Rust 物理 + 真实碰撞数据（brushJson + **triJson** + 传送表），起点取 owner 路径首采样

### 7.4 遗留（未做，需owner 裁决）

修后玩家走到 facet 交界处**不再被抬上去，而是停在低地**（实测 z 停在 ≈ −9789 附近不再前进）。
那 11.55 HU 的落差是 `.phy` 凸包把曲面坡压成大平面的必然结果（§3.3）。要不要让玩家**跨上去**，
是一个策略问题而不是缺陷修复：

- **A. 保持现状**：凸包落差处不跨越，走不过去就停下。
- **B. 收紧 `STEP_HEIGHT`**：让「明确跨不上去」变成硬规则，减少误判。
- **C. 改几何**：模型碰撞从 `.phy` 凸包换成 `export_model_tri_colliders()`（可视网格三角），
  曲面坡由密集三角形表达。代价是三角形数量与碰撞成本上升。

C 能真正解决「坡顶能不能站」这一类问题，A/B 只能避免被弹飞。
