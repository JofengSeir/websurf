**修法 B 已被实测否掉**；病灶疑在 `check_stuck` 用了整身体盒，见 §7.1）
**发现日期**：2026-10-05
**归属实测日期**：2026-10-05

**相关**：`06-phy-hull-facet-jump.md`（同一条坡上的弹飞，已处置）

## 1. 症状

owner 在 `s1_ramp1b` 的坡上沿 −z 行走，走到 z ≈ −9789 处**完全停住**，卡 3.5 秒不动。
位置全程 `y = 14560.03` 恒定，`on_ground = true`，没有弹飞。

owner 路径文件 `phys-path-20261005-120800.json`：

- `render` 470 样本，最后一次 z 减小在 index 257（z = −9786.37），之后 212 个采样不动；
- `tick` 447 样本（**worker 权威帧**），最后一次 z 减小在 index 248（z = −9786.36），之后 198 个采样不动。

**两条链停在同一个 z** ⇒ 不是渲染、不是插值、不是录制结束，是权威物理自己不走了。
且 index 120~134 还在 −9790.3 ~ −9790.9 之间每采样弹 ±0.6 HU，是「顶着什么、推不动、来回蹭」。

## 2. 先排除的：几何障碍

`debug_trace` 从卡住的位置沿 −z 做 **60 HU** 长扫掠：

```
z = -9786.4 / -9790 / -9795 / -9800，脚下 +0/+2/+6/+12/+20/+40/+60 各高度：全部 fraction = 1.0
脚下 14560.03 有一张水平可站面 (0,1,0) 连续铺到至少 z = -9850
```

**60 HU 内没有任何几何障碍。** 所以不是墙、不是台阶。

> 走过的弯路：先用 **3.9 HU**（一步的距离）扫掠，结论是「畅通」——**那是错的**，够不到
> 5 HU 外的障碍。判断「有没有东西挡路」必须用远大于一步的长扫掠。

`detect_blocked_move` 也排除：它要求 `!on_ground`，而玩家全程 `on_ground = true`。

## 3. 实测：两个碰撞查询在同一位置给出相反答案

为此新增了诊断绑定 `PhysWorld::debug_position_probe`（见 §5），在同一 tick 上并置两种查询。
从 owner 起点走到停下，逐 tick 探测：

```
 tick      z          y     free  downFrac  n.y    state
    0   -9590.90  14560.03   1    0.0000  0.000  ground
   40   -9734.46  14560.03   1    0.0000  0.000  ground
   55   -9789.06  14560.03   0    0.0000  0.000  ground   <== free 翻成 0
   56   -9788.96  14560.03   0    0.0000  0.000  ground
  ...
   80   -9790.71  14560.03   0    0.0000  0.000  ground   <== 每 tick 抖 ±0.1 HU
```

**z ≈ −9789 处 `is_position_free` 从 1 翻成 0，而 `trace` 说脚下就有地面、`on_ground` 仍为 true。**
之后的每 tick 位移只有 ±0.1 HU，正是 owner 路径里看到的来回蹭。

把探针沿 y 抬起来看范围：

```
y=14560.03 (+ 0)  is_position_free=0
y=14561.03 (+ 1)  is_position_free=0
y=14564.03 (+ 4)  is_position_free=0
y=14568.03 (+ 8)  is_position_free=0
y=14576.03 (+16)  is_position_free=1     <-- 抬到 +16 才脱身
对照 z=-9600（正常段）：y=14560.03 / +1 / +4 全部 free=1
```

**⇒ 那个位置的 y ∈ [约 14560, 约 14568] 区间里有实体**，玩家 72 HU 高的身体箱（14560..14632）
与之相交，`is_position_free` 如实报「不空」。

## 4. 机制：`check_stuck` 冻结

`player::check_stuck`（`src/phys/player.rs`）：

```rust
if world.is_position_free(&p.origin, &mins, &maxs) { p.stuck_ticks = 0; return false; }
// 60 个挤出候选（dist ∈ {1,2,4,8,16,34} × STUCK_DIRS 10 向）
// 某个候选空闲就把 origin 挪过去并 return false
p.stuck_ticks += 1; p.velocity = [0,0,0]; true   // <- 全部失败
```

返回 true 时 `player_tick` **跳过本 tick 的全部移动与落地判定**。

在 owner 这个位置上，60 个候选点里总有几个「空闲」（往 +x / ±z 挪 1~2 HU 就出去了），
于是每 tick：判定不空 → 挪 1~2 HU → 下一 tick 前进被同样的实体挡住 → 再挪回去。
**净位移 ≈ 0，表现为原地抖动。** 这与实测的 ±0.1 HU/tick、以及 owner 路径里的来回蹭完全一致。

**⇒ 卡住的直接机制确认：`check_stuck` 每 tick 把玩家挤出一点点，抵消了前进。**

## 5. 新增的诊断能力

三个绑定，都在 `src/phys/mod.rs`，都不推进物理、不改任何状态。

### 5.1 `debug_position_probe(x, y, z)` → 6 个数

| 下标 | 含义 |
|---|---|
| 0 | `is_position_free`（1 = 空，0 = 不空） |
| 1 | 原地向下扫掠 1 HU 的 `fraction` |
| 2..4 | 该扫掠命中的法线 |
| 5 | `stuck_ticks` |

**为什么需要它**：移动走 `World::trace`，而 `check_stuck` 走 `World::is_position_free`——
**两个独立的查询**。没有并置观测就无法发现它们不一致。本条问题的定位就是靠它起步的。

### 5.2 `debug_collide_attrib(x, y, z)` → 18 个数（归属）

| 下标 | 含义 |
|---|---|
| 0 | 空闲（1）/ 不空闲（0） |
| 1 | brush 命中数（**逐个候选**判实心的数量，非 broadphase 候选数） |
| 2 | 三角形命中数（同上） |
| 3..5 | 第一个实心 brush 的 AABB min xyz（brush 不带名字，靠 AABB 人工比对） |
| 6..8 | 第一个实心 brush 的 AABB max xyz |
| 9 | 有三角形命中（1/0） |
| 10 | 三角形所属网格在 `tri_meshes` 的下标（无命中时 −1） |
| 11..13 | 第一个实心三角形的 AABB min xyz |
| 14..16 | 第一个实心三角形的 AABB max xyz |
| 17 | 该三角形在网格 `indices` 里的首个顶点下标 |

**归属是逐候选单独判的**，且刻意用与 `is_position_free` **完全相同的谓词**（各自单传一个候选
去调 `trace_box` / `trace_box_tri_entries` 看 `start_solid`）——若改用 `box_in_brush` 之类另一套
判定，报出的归属就会与实际判决脱节，这份诊断不可信。代价是 O(候选数) 次扫掠，**仅供诊断**，
`is_position_free` 的热路径不经过它。

### 5.3 `debug_tri_mesh_name(index)` → `String`

取 `tri_meshes` 第 `index` 个网格的模型名（形如 `models/props/666/s1_ramp1b.mdl`），配套
5.2 的下标 10 使用。

**为此改了两处数据结构**：
- `TriMesh` 加 `name` 字段。此前 `parse_tri_meshes` 的 `WasmTriMesh` **没有声明**它，serde 按
  默认忽略未知字段 —— `export_model_phy_colliders` 明明吐了 `name`，落地后却查不到「这条三角形
  属于哪个模型」。
- `TriEntry` 加 `mesh_index`。**不能靠 `Rc` 指针反查**：`mesh` 是 `Rc::new(mesh.clone())`
  克隆出来的，地址与 `World::tri_meshes` 里的原对象必然不同，按 `as_ptr` 比对永远失配。
  第一版就是这么写的，实测 `mesh_index` 恒为 −1，已改。

### 5.4 `debug_stuck_probe(x?, y?, z?)` → 13 个数（挤出重放）

| 下标 | 含义 |
|---|---|
| 0 | 该点是否空闲（1/0） |
| 1..3 | 会选中候选的位移 dx / dy / dz（无胜出为 −999） |
| 4 | 该候选的 `dist`（无胜出为 −1） |
| 5 | 该候选在 `STUCK_DIRS` 里的下标（无胜出为 −1） |
| 6 | 试到第几个候选才成功（含命中的那一个，从 1 起；无胜出时为尝试总数） |
| 7..11 | `dist = 1` 时 +y / +x / −x / +z / −z 各自是否空闲（1/0） |

**只读重放** `check_stuck` 的候选枚举，共用同一份 `STUCK_DIRS` 与同一组距离常量，所以
「它选中什么」就是「`check_stuck` 会选中什么」——两者日后若分叉，本函数的可信度随之失效。
坐标可省略，省略时用玩家当前 `origin`（与 `check_stuck` 的输入一致）；**不省略就能探任意位置
而不必先挪玩家**，这也是「沿 y 抬高探针扫描」这类测量能做的前提。

用法示例（Node，wasm 直驱）：

```js
const a = pw.debug_collide_attrib(x, y, z);   // 谁在挡
const s = pw.debug_stuck_probe(x, y, z);      // 会往哪挤
if (a[0] === 0 && a[2] > 0) {
  console.log(pw.debug_tri_mesh_name(a[10])); // 哪个模型
}
```

## 6. 归属实测（2026-10-05，待裁决第 ① 条已结）

从 owner 起点逐 tick 走到卡住（`test/maps/surf_666.bsp`，wasm 直驱）：

```
卡死在 tick 55，位置 (-13535.12, 14560.03, -9789.06)
brush 命中 0    tri 命中 2                      ← 是三角网格，不是世界 brush
归属            models/props/666/s1_ramp1b.mdl（tri_meshes 下标 205）
命中三角形 AABB  x -13984..-13536.00   y 13983.90..14571.57   z -9962.09..-9802.85
玩家盒          x -13551.12..-13519.12   y 14560.03..14632.03
```

**排除世界 brush 的 chamfer / 端盖** —— brush 命中数为 0。**就是 `s1_ramp1b` 的 .phy 凸包。**

两轴的重叠量：

| 轴 | 玩家盒 | 命中三角形 | 重叠 |
|---|---|---|---|
| x | −13551.12 .. −13519.12 | −13984.00 .. **−13536.00** | **15.12 HU 的窄条** |
| y | 14560.03 .. 14632.03 | 13983.90 .. **14571.57** | **11.54 HU** |

三角形 x 上界正好 −13536.00，玩家 origin 在 −13535.12 —— **站在模型边缘外 0.88 HU 处**，
身体向 −x 探出的 15 HU 探进了模型里。

**不是容差误判**：把探针沿 y 抬高 0.05 / 0.1 / 0.2 / 0.3 / 0.5 / 1 / 2 HU，**全部仍判不空**，
要抬到 **+12 HU** 才自由。所以 `start_solid` 的容差没问题，**盒体是真的陷在实体里**。

### 6.1 挤出选择：B 案被实测否掉

```
dist = 1 的五个轴向候选： +y=0   +x=0   -x=0   +z=0   -z=0      ← 全部被堵
最终选中 STUCK_DIRS 下标 3（= +z，身后方向），dist = 4，试到第 24 个候选才成功
```

**`STUCK_DIRS[0]` 就是上方向**（`player.rs` 的常量第一项 `[0.0, 1.0, 0.0]`），且 `dist` 是外层
循环 —— 所以每个距离都**先试 +y**。既然最终仍被推向 +z，就说明**上方向在 dist 1 / 2 / 4 全被堵**，
横向在 1 / 2 HU 也被堵，唯一近路是身后 4 HU。

**⇒ 「被往两边推」不是方向挑错了，是四周只剩那一个出口。** 因为凸包在玩家脚底之上 11.5 HU 处
仍在延伸，抬不动；横向被模型边缘占满。

**原 ② 条的 B 案（挤出方向改为沿当前速度的反方向）据此作废**：

- 本例速度就是 −z，沿速度反方向**正是 +z**，与现状完全相同 —— B 改不动它；
- owner 描述的「站在尖脊上不动、被往两边推」场景里**速度为零**，B 根本没有方向可用。

## 7. 未决（下一步）

1. **判据本身是否选错了盒 —— 新增，优先级最高**。`check_stuck` 问的是
   「我整个 **72 HU 高**的身体盒空不空」，而玩家盒的 z 半伸是 **54 HU**：站在 z=−9789 时身体
   已覆盖到 z=−9843，而那里的坡面比脚底高 11.5 HU。

   **⇒ 在任何一个「前方地面比脚下高」的坡上，这个判据都会报「卡在实体里」**，
   它把「前方是上坡」误读成「我卡住了」。这与 §6 的实测完全吻合。

   **待测**：用**贴地小盒**（而非整身体盒）重判卡住点。若小盒报空闲 ⇒ 病灶坐实在盒高，
   修法是让 `check_stuck` 改用小盒（局部改动、可测）；若小盒仍不空 ⇒ 真是几何问题，走 ③。
