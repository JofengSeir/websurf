脚下 14560.03 有一张水平可站面 (0,1,0) 连续铺到至少 z = -9850

## 4. 机制：`check_stuck` 冻结

`player::check_stuck`（`src/phys/player.rs`）：

```rust
if world.is_position_free(&p.origin, &mins, &maxs) { p.stuck_ticks = 0; return false; }
// 60 个挤出候选（dist ∈ {1,2,4,8,16,34} × STUCK_DIRS 10 向）
// 某个候选空闲就把 origin 挪过去并 return false
p.stuck_ticks += 1; p.velocity = [0,0,0]; true   // <- 全部失败
```

返回 true 时 `player_tick` **跳过本 tick 的全部移动与落地判定**。

在 owner 这个位置上，60 个候选点里总有几个「空闲」（往 +x / ±z 挪 1~2 HU 就出去了），
于是每 tick：判定不空 → 挪 1~2 HU → 下一 tick 前进被同样的实体挡住 → 再挪回去。
**净位移 ≈ 0，表现为原地抖动。** 这与实测的 ±0.1 HU/tick、以及 owner 路径里的来回蹭完全一致。

**⇒ 卡住的直接机制确认：`check_stuck` 每 tick 把玩家挤出一点点，抵消了前进。**

## 5. 新增的诊断能力

三个绑定，都在 `src/phys/mod.rs`，都不推进物理、不改任何状态。

### 5.1 `debug_position_probe(x, y, z)` → 6 个数

| 下标 | 含义 |
|---|---|
| 0 | `is_position_free`（1 = 空，0 = 不空） |
| 1 | 原地向下扫掠 1 HU 的 `fraction` |
| 2..4 | 该扫掠命中的法线 |
| 5 | `stuck_ticks` |

**为什么需要它**：移动走 `World::trace`，而 `check_stuck` 走 `World::is_position_free`——
**两个独立的查询**。没有并置观测就无法发现它们不一致。本条问题的定位就是靠它起步的。

### 5.2 `debug_collide_attrib(x, y, z)` → 18 个数（归属）

| 下标 | 含义 |
|---|---|
| 0 | 空闲（1）/ 不空闲（0） |
| 1 | brush 命中数（**逐个候选**判实心的数量，非 broadphase 候选数） |
| 2 | 三角形命中数（同上） |
| 3..5 | 第一个实心 brush 的 AABB min xyz（brush 不带名字，靠 AABB 人工比对） |
| 6..8 | 第一个实心 brush 的 AABB max xyz |
| 9 | 有三角形命中（1/0） |
| 10 | 三角形所属网格在 `tri_meshes` 的下标（无命中时 −1） |
| 11..13 | 第一个实心三角形的 AABB min xyz |
| 14..16 | 第一个实心三角形的 AABB max xyz |
| 17 | 该三角形在网格 `indices` 里的首个顶点下标 |

**归属是逐候选单独判的**，且刻意用与 `is_position_free` **完全相同的谓词**（各自单传一个候选
去调 `trace_box` / `trace_box_tri_entries` 看 `start_solid`）——若改用 `box_in_brush` 之类另一套
判定，报出的归属就会与实际判决脱节，这份诊断不可信。代价是 O(候选数) 次扫掠，**仅供诊断**，
`is_position_free` 的热路径不经过它。

### 5.3 `debug_tri_mesh_name(index)` → `String`

取 `tri_meshes` 第 `index` 个网格的模型名（形如 `models/props/666/s1_ramp1b.mdl`），配套
5.2 的下标 10 使用。

**为此改了两处数据结构**：
- `TriMesh` 加 `name` 字段。此前 `parse_tri_meshes` 的 `WasmTriMesh` **没有声明**它，serde 按
  默认忽略未知字段 —— `export_model_phy_colliders` 明明吐了 `name`，落地后却查不到「这条三角形
  属于哪个模型」。
- `TriEntry` 加 `mesh_index`。**不能靠 `Rc` 指针反查**：`mesh` 是 `Rc::new(mesh.clone())`
  克隆出来的，地址与 `World::tri_meshes` 里的原对象必然不同，按 `as_ptr` 比对永远失配。
  第一版就是这么写的，实测 `mesh_index` 恒为 −1，已改。

### 5.4 `debug_stuck_probe(x?, y?, z?)` → 13 个数（挤出重放）

| 下标 | 含义 |
|---|---|
| 0 | 该点是否空闲（1/0） |
| 1..3 | 会选中候选的位移 dx / dy / dz（无胜出为 −999） |
| 4 | 该候选的 `dist`（无胜出为 −1） |
| 5 | 该候选在 `STUCK_DIRS` 里的下标（无胜出为 −1） |
| 6 | 试到第几个候选才成功（含命中的那一个，从 1 起；无胜出时为尝试总数） |
| 7..11 | `dist = 1` 时 +y / +x / −x / +z / −z 各自是否空闲（1/0） |

**只读重放** `check_stuck` 的候选枚举，共用同一份 `STUCK_DIRS` 与同一组距离常量，所以
「它选中什么」就是「`check_stuck` 会选中什么」——两者日后若分叉，本函数的可信度随之失效。
坐标可省略，省略时用玩家当前 `origin`（与 `check_stuck` 的输入一致）；**不省略就能探任意位置
而不必先挪玩家**，这也是「沿 y 抬高探针扫描」这类测量能做的前提。

用法示例（Node，wasm 直驱）：

```js
const a = pw.debug_collide_attrib(x, y, z);   // 谁在挡
const s = pw.debug_stuck_probe(x, y, z);      // 会往哪挤
if (a[0] === 0 && a[2] > 0) {
  console.log(pw.debug_tri_mesh_name(a[10])); // 哪个模型
}
```

### 5.5 `debug_free_table(x, feet_y, z, half_x, max_h, max_hz)`

盒尺寸敏感性扫描。盒**底面**钉在 `feet_y`：`origin = [x, feet_y, z]`、
`mins = [-half_x, 0, -hz]`、`maxs = [half_x, h, hz]`，于是盒恰跨 y 从 `feet_y` 到 `feet_y + h`。
逐格独立调 `is_position_free`，返回 `(max_h + 1) * (max_hz + 1)` 个 0/1，**行优先**：
第 `hi * (max_hz + 1) + zi` 格 = 盒高 `hi`、z 半伸 `zi` 时是否空闲。**不推进物理、不改状态。**

### 5.6 `debug_hull()` → 6 个数

玩家**当前**碰撞箱的 `[min_x, min_y, min_z, max_x, max_y, max_z]`。

**为什么需要它**：`set_hull(half_width, stand_height, duck_height)` 的**第三个参数是蹲下高度，
不是 z 向伸长** —— `player::apply_hull` 把 z 半伸直接取成 `half_width`。我此前好几轮都把
`54` 当成 z 半伸写进了文档与分析，是错的；本绑定给出真值（见 §7.0）。

### 5.7 `debug_normal_escape(x, y, z, nx, ny, nz, max_d)`

「沿指定方向能否脱身」的扫描。对 `d = 1..=max_d` 每个整数距离记两个数：① `World::trace` 沿
该方向扫 `d` HU 的 `fraction`；② 扫掠终点 `is_position_free` 是否空闲（1/0）。返回 `2 * max_d`
个数成对存放：**第 `2*(d-1)` 项是 fraction、第 `2*(d-1)+1` 项是终点空闲标记**。
`fraction = 1.0` 表示这一步没被任何东西挡住。

**两个数都要**：只有 fraction = 1 不够（沿法线抬起后仍可能落在实体里）；只有终点空闲也不够
（终点可能在实体另一侧、中间隔着材料）。**两个同时成立**才等于「这一步真的能脱身」。

这是修法 E 的实测入口 —— **E 已被它否掉，见 §7.3。**

### 6.1 挤出选择：B 案被实测否掉

```
dist = 1 的五个轴向候选： +y=0   +x=0   -x=0   +z=0   -z=0      ← 全部被堵
最终选中 STUCK_DIRS 下标 3（= +z，身后方向），dist = 4，试到第 24 个候选才成功
```

**`STUCK_DIRS[0]` 就是上方向**（`player.rs` 的常量第一项 `[0.0, 1.0, 0.0]`），且 `dist` 是外层
循环 —— 所以每个距离都**先试 +y**。既然最终仍被推向 +z，就说明**上方向在 dist 1 / 2 / 4 全被堵**，
横向在 1 / 2 HU 也被堵，唯一近路是身后 4 HU。

**⇒ 「被往两边推」不是方向挑错了，是四周只剩那一个出口。** 因为凸包在玩家脚底之上 11.5 HU 处
仍在延伸，抬不动；横向被模型边缘占满。

**原 ② 条的 B 案（挤出方向改为沿当前速度的反方向）据此作废**：

- 本例速度就是 −z，沿速度反方向**正是 +z**，与现状完全相同 —— B 改不动它；
- owner 描述的「站在尖脊上不动、被往两边推」场景里**速度为零**，B 根本没有方向可用。

## 7. 判据的盒尺寸敏感性扫描（2026-10-05 实测，④ 已测完）

### 7.0 先更正一处此前的错误推断

前几轮我反复说「玩家盒 z 半伸是 **54 HU**，身体向前探出 54 HU」。**那是错的。**
`set_hull(half_width, stand_height, duck_height)` 的**第三个参数是蹲下高度，不是 z 向伸长**：

```rust
// src/phys/player.rs 的 apply_hull
p.stand_mins = [-half_width, 0.0, -half_width];
p.stand_maxs = [half_width, stand_height, half_width];
```

z 半伸直接取 `half_width`。所以 `set_hull(16, 72, 54)` 的**站立盒是 32 × 72 × 32**
（x × y × z），**z 半伸 = 16**。新增只读绑定 `debug_hull()` 返回玩家当前箱的六个分量，
免得再靠推测：

```
mins [-16.0, 0.0, -16.0]   maxs [16.0, 72.0, 16.0]     => z 半伸 = 16
```

逐格独立调 `is_position_free`，返回 `(max_h+1) × (max_hz+1)` 的 0/1 表（行优先）。

1. **盒高从 0 扫到 90，八行完全相同** ⇒ **高度对判定零影响**。

而那一小片坡面比脚底高 11.5 HU，于是身体盒下段与之相交。实测挤出的脱身点是 `+z dist=4`
（> 2.2 HU 的重叠量，与 `dist ∈ {1,2,4,...}` 里第一个够大的值吻合）。

沿 z 从 −9600 扫到 −9900（步长 10，脚底钉在 14560.03），`#` = 阻塞：

- **z ≤ -9810**：`hz = 0` 也阻塞。**但这不能算判据问题** —— 本扫描把脚底钉死在 14560.03，

### 7.3 修法 E 的实测：被否掉，两条独立理由

新增只读绑定 `debug_normal_escape(x, y, z, nx, ny, nz, max_d)`：对 `d = 1..=max_d` 逐步记两个数
——① `World::trace` 沿该方向扫 `d` HU 的 `fraction`；② 扫掠终点 `is_position_free` 是否空闲。
**两个数必须同时成立**才算「这一步真的能脱身」：只有 fraction = 1 不够（沿法线抬起后仍可能落在
实体里，§7.1 已实测抬 1~8 HU 全不空闲）；只有终点空闲也不够（终点可能在实体另一侧、中间隔着材料）。

#### 理由一：`trace` 在结构上测不出「嵌入」

把玩家沉到 brush 面下 **4 HU**（实测 `free=0`、`brush=1`、`tri=3`，确定在实心材料里），沿 +y 扫：

```
沉 4 HU，沿 +y：d = 1 .. 24    trace frac 全部 = 1.000
```

**在实心材料内部 4 HU 处，`trace` 依然报「完全通畅」。** 因为 `trace` 只 clip 它**穿过**的平面，
嵌在内部时它一个平面都没穿过。

**⇒ E 用错了原语。** `check_stuck` 选用 `is_position_free` 不是随意挑的：它是当前**唯一能检出
嵌入**的查询，换成 `trace` 这条路走不通。

**顺带厘清本文标题那个说法**：两个查询给出相反答案，是因为它们**回答的根本不是同一个问题** ——
`trace` 答「能不能穿过」，`is_position_free` 答「现在是不是在里面」。在嵌入状态下二者必然不一致，
这不是缺陷。

#### 理由二：只看终点空闲，E 也不成立

| 位置 | 沿 ground_normal 真正脱身的最小距离 |
|---|---|
| 卡死点（**误报**，`tri=2`） | **12 HU** |
| 沉 4 HU（**真嵌入**，`brush=1 tri=3`） | **16 HU** |

- **不区分**：两者都是「往上抬出来」，中间只有 **4 HU 余量**，是个魔数。
- **会把弹飞 bug 请回来**：卡死点要抬 **12 HU** 才脱身 —— 这正是 `9cceec9` 修掉的
  「`step_move` 无条件抬 18 HU」那一类瞬移。**实现 E 等于重新引入 12 HU 的弹射。**

另测了 E2（沿移动方向 −z 脱身）：**20 HU 内永远脱不了身** —— 前面确实有坡挡着，E2 会给出
「卡住」的现判，等于没改。

**⇒ E 作废。** 但这轮测量反而收紧了剩下两条的取舍依据：

**`trace` 测不出嵌入 ⇒ 判据只能建立在 `is_position_free` 上 ⇒ 能改的只有「何时该信这个判决」，
而不是「用哪个查询」或「盒多大」。** 按这条筛：

- **D**（缩小探测盒深度）改的是判据本身，且要付出窄缝漏检 —— 与上面的结论方向相反，但改动
  最小，仍是候选。
- **A**（只在 `!on_ground` 时启用）**正是改「何时该信这个判决」**，与结论同向。

**⇒ 首选 A。**
