# 02 · chamfer 黄线框靠「重新猜」得到，与物理侧的平面表不是同一套判据

**状态**：见 TODO.md T-502（迁移前自述「待裁决」）
**取证日期**：2026-10-04
**关联**：[01](01-chamfer-is-not-a-bevel.md)（物理侧根本没有倒角）——建议与 01 同一次改动落地

---

## 1. 现象

即使不谈 01 的物理问题，可视化本身也不忠实于它声称要画的东西：

- 它不读物理侧实际使用的 chamfer 平面列表，而是拿 `brush.planes`（真实面 + chamfer 面混在一起）
  **用自己的一套阈值重新猜**哪些平面是 chamfer；
- 它判定「朝外」用的不是凸包本身，而是 **brush 的 AABB 中心**。

结果是同一条棱在不同 brush 上会画出不同朝向、不同取舍的黄框。

## 2. 证据

### 2.1 两套独立阈值，宽松程度差 5 倍

| 用途 | 常量 | 值 | 位置 |
|---|---|---|---|
| 生成侧：顶点是否落在某平面上 | `eps_plane` | **0.1** | `apps/debug/crates/wasm/src/lib.rs:2890` |
| 显示侧：顶点是否落在某平面上 | `FACE_EPS` | **0.5** | `apps/debug/src/renderer/collider-debug.ts:95` |

显示侧的 `computeChamferStrips`（`collider-debug.ts:307`-`:355`）用 `FACE_EPS` 收集面上顶点
（`:308`），而物理侧用 `eps_plane` 收集同一批顶点。两者对「哪些顶点算在平面上」的判断不一致。

### 2.2 显示侧重新判定 chamfer，而不是接收 chamfer 列表

`computeChamferStrips` 的判据是：

1. 面上顶点 ≥ 2（`:310`）；
2. 取相距最远的一对作棱（`:312`-`:318`）；
3. 其余面上顶点到棱线的垂距全部 ≤ `CHAMFER_COLLINEAR_EPS = 0.5`（`:279`, `:325`-`:337`）；
4. 不共线则 `continue`（`:338`）。

这是**又一套启发式**，与物理侧的生成判据（平面法线 = 两面法线均值 + 外凸校验）完全不同。
两个方向的分叉都会发生：

- 物理侧有、显示侧判不出 → 该棱的黄框缺失（局部缺边）；
- 显示侧判成、物理侧没有 → 凭空多出黄框（例如极薄 sliver 面上，其余顶点恰好落在对角线 0.5 HU 内）。

代码自己承认了这两套判据不重合（`collider-debug.ts:271`-`:273`）：

> 注意判据不完全重合：`computeChamferStrips` 允许 ≥ 2 个顶点加共线校验，而 `orderedFaces` 只按
> 「顶点数 ≥ 3」筛选，故共线三点以上的 chamfer 平面也会进入线框

但该注释只覆盖了「共线点数」这一种分歧，没有覆盖上面 2.1 的容差差与 2.3 的朝向问题。

### 2.3 朝外方向用 AABB 中心，对非盒状 brush 会选错

`rebuildChamfers` 外推四边形时（该方法已于 2026-10-05 删除，行号不再有效，故此处只留符号名）：

```ts
// 平面内且 ⊥ 棱的方向 = n × e
let dx = s.n[1] * ez - s.n[2] * ey; /* … dy, dz … */
// 定号：该方向若指向 brush 的 AABB 中心一侧则整体取反，保证朝外
const mdx = (s.a[0] + s.b[0]) / 2 - (brush.min.x + brush.max.x) / 2;
```

「朝外」的正确参照是**凸包内部**，用凸包顶点均值（centroid）才成立；这里用的是
**brush AABB 中心**（`collider-adapter.ts` 给出的 `min`/`max`）。对 L 形、楔形、长条斜坡这类
brush，AABB 中心不落在凸包的核心区，于是在不同棱上判反，把 16 HU 的四边形推到凸包**内侧**。

因为线框用 `depthTest: false` 画（`collider-debug.ts:276` 头注），推错的黄框照样可见，
表现为「有一段框飘在不该在的位置」。

### 2.4 四边形尺寸是显示常量，与物理无关

`CHAMFER_QUAD_LEN = 16`（`collider-debug.ts:286`），头注明确「只影响可视化尺寸，不参与任何判定」。
在 01 已确认 chamfer 削减体积为零的前提下，这 16 HU 的框**不代表任何碰撞面**，
只是「这条棱在这里」的一个箭头式标记。

## 3. 根因

可视化没有「读取物理真相」这条通路，而是从同一份输入（`brush.planes`）用另一套启发式反推。
两套启发式的容差与参照系都不同，必然在边界情况上分叉。

## 4. 影响面

- owner 报的「顶部有一块黄色边框只有左边有」，与 2.2 的「局部缺边」和 2.3 的「朝向推错」都吻合；
  在 `surf_666` 这种大规模 map 上，`chamferViewDistance = 0`（全量）时实测单帧绘制 **6498** 个
  chamfer 平面（控制台 `[collider-debug] chamfer 重建: 距离=0 平面=6498`），取样密度足以让任一
  分叉在画面上显眼。
- 只影响 debug 工程的可视化，不影响物理。

## 5. 建议处置（与 01 绑定）

1. **让物理侧把 chamfer 平面显式带出来**：在 `WasmBrushPlane` 上加一个 `is_chamfer: bool`
   （或单独一个 chamfer 平面数组），可视化直接读，不再反推。这样 2.1 / 2.2 同时消解。
2. **朝向改用凸包 centroid**：`computeBrushHull(brush)` 的顶点均值替代 AABB 中心，消解 2.3。
3. 选 01 的方案 A 时，四边形长度应按真实倒角宽度画，而不是固定 16 HU。
4. 若短期不动物理，至少把 `collider-debug.ts:267`-`:276` 的头注按实测改写——
   当前「既进物理碰撞」「角平分线 chamfer 呈现为贴坡倒角」两句都会让人以为存在真实倒角。
## 6. 处置结果（2026-10-05，已完成）

本篇的三条分叉（容差差 5 倍、启发式重判、朝向用 AABB 中心）随「黄色 chamfer 线框整路删除」
一并消失，不需要单独修：

- §2.1 容差差、§2.2 重新判定 —— 载体是 computeChamferStrips，已删；
- §2.3 朝向参照 AABB 中心 —— 载体是 ebuildChamfers 的四边形装配，已删；
- §2.4 CHAMFER_QUAD_LEN = 16 这个「不代表任何碰撞面」的显示常量，已删。

**根因层面的处置**：面高亮的判据不再由渲染端反推，而是由物理侧逐平面给出
is_real_face（见 [01](01-chamfer-is-not-a-bevel.md) §6 与 plane_is_real_face）。
orderedFaces 现在的第一道判据就是 p.isRealFace !== true → continue，
即「不是物理真实面就不画」成为渲染侧的默认行为，而不是某个开关下的特例。

FACE_EPS（collider-debug.ts:95）保留，但语义已收窄为「把凸包顶点归到已放行的面上」，
不再参与「是不是面」的判断。
